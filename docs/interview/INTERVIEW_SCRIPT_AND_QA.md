# CQUPT-SRC 面试讲稿与高频问答

## 1. 30 秒版本

我做的是一个校园 SRC 漏洞响应与安全学习平台，核心是把学生提交漏洞、审核员审核、修复复测、归档证书和积分激励串成完整闭环。技术上采用 React、NestJS、PostgreSQL/Prisma 和 MinIO。项目的难点不是普通 CRUD，而是权限与审计、漏洞状态机，以及 AI 助手和自动复测的安全边界。AI 只负责语言与推理，实时事实、权限和所有写操作都由后端控制；自动复测又拆成低风险 Runner 和需要人工审批的 Hermes Direct 两条通道。

## 2. 2 分钟版本

这个项目面向校园安全运营，有学生、审核员和管理员三类角色。

学生需要先签责任书并通过安全答题，之后才能提交漏洞。审核员可以要求补充、确认等级和积分、推动修复并复测；管理员负责用户、公告、证书、商城、审计和系统配置。漏洞的每次状态变化既记录业务事件，也写安全审计，关键积分、库存和状态操作都在数据库事务中完成。

架构上是 React 前端、NestJS 模块化单体后端、PostgreSQL/Prisma、MinIO。采用模块化单体是因为业务事务和领域关系很强，当前规模下比微服务更容易保证一致性；高风险执行能力则独立出去。

AI 有三部分。第一是“邮宝”助手，前端不直连模型，所有请求经过后端 AI Gateway。实时积分、库存、漏洞状态由后端确定性查询，模型只处理开放式问题。第二是知识沉淀，只有用户确认已解决的问题会话才会经过脱敏、总结、评分、去重和审核进入知识库，用户对话不能自动变成 Skill。第三是 AI 漏洞复测，低风险步骤交给受限 Runner，高风险复杂步骤交给独立 Hermes Direct，并经过方案审批、逐动作审批、目标范围限制、凭据加密和证据约束。

目前项目的主要改进点是完成 Refresh Token 闭环、把进程内轮询 Worker 迁移到可靠队列、统一快速迭代造成的文档漂移，并拆分几个过大的 Service 和页面。

## 3. 5 分钟结构

按以下顺序讲，避免陷入页面功能枚举：

1. 背景：校园漏洞响应需要合规、效率、激励和可追责。
2. 用户：学生、审核员、管理员。
3. 主链路：准入 -> 提交 -> 审核 -> 修复 -> 复测 -> 归档 -> 证书/积分。
4. 架构：模块化单体 + 外置高风险执行器。
5. 两个技术难点：状态一致性；AI 安全边界。
6. 质量保障：事务、RBAC、审计、E2E、状态机测试。
7. 不足与下一步：Refresh Token、队列、文档、拆分大文件、生产部署。

## 4. STAR 项目亮点

### 亮点一：AI 自动复测安全架构

**Situation：** 普通 AI 助手只能生成建议，真正自动复测会触碰目标越权、凭据泄露和高危动作风险。

**Task：** 在不让模型获得无限执行权的前提下，支持自动生成计划、执行低风险步骤，并让复杂步骤可控执行。

**Action：**

- 拆成 PLAN_ONLY、CONTROLLED_RUN、HERMES_DIRECT。
- 策略引擎逐步骤判断 ALLOW、REQUIRE_HUMAN_APPROVAL、BLOCK。
- 高风险动作逐次审批。
- 目标范围经过同源、DNS、端口和私网地址检查。
- 凭据使用 AES-256-GCM，AAD 绑定任务和目标。
- 执行结论必须引用 artifact/证据。
- 任务状态、审批和证据访问写审计。

**Result：** 形成了从计划、策略、审批、执行到统一报告的闭环，并有 Runner 和 Egress Policy 自动测试。

### 亮点二：AI 知识治理

**Situation：** 直接把聊天记录当知识会导致隐私泄露、错误固化、重复内容和知识投毒。

**Task：** 让有价值的已解决问题可复用，同时不能暴露用户原始上下文。

**Action：**

- 以 Problem Session 而不是单轮消息为沉淀单位。
- 仅处理用户确认已解决的会话。
- 脱敏、泛化、评分、聚类、去重。
- 管理员审核或严格阈值自动入库。
- 用户来源知识禁止自动晋升 Skill。
- 建立 revision、feedback、maintenance task。

**Result：** 知识库、会话审核、维护和 Skill Candidate 形成分层，不让模型直接改变长期能力。

### 亮点三：事务型积分商城

**Situation：** 库存和积分如果分别更新，失败时会产生超卖或余额不一致。

**Task：** 保证兑换、取消和审计的一致性。

**Action：** 使用 Prisma Transaction 同时校验余额/库存、扣减、写账本、创建兑换记录和审计；取消时做逆向补偿。

**Result：** 账务可追踪，失败可以整体回滚。

## 5. 高频技术问答

### Q1：为什么不使用微服务？

当前核心业务围绕同一个用户、漏洞、积分和审计数据库，事务关系紧密，团队和流量规模还不足以抵消微服务的网络、部署、观测和分布式一致性成本。因此选择 NestJS 模块化单体。对于风险边界明显不同的执行能力，例如自动复测 Runner 和 Hermes Direct，再进行进程/容器隔离。

### Q2：为什么同时有 VulnerabilityEvent 和 AuditLog？

`VulnerabilityEvent` 是领域事件时间线，描述漏洞从什么状态变到什么状态；`AuditLog` 是平台级安全审计，记录谁在什么请求中对哪个对象做了什么，包含 IP、User-Agent、结果和元数据。两者受众和保留目的不同。

### Q3：如何防止前端越权？

前端菜单隐藏不是安全措施。后端每个受保护接口先过 `JwtAuthGuard`，重新查询用户状态和实时权限，再由 `PermissionsGuard` 检查 `@RequirePermissions`。涉及自己的资源还要在 Service 中校验 ownership。提交漏洞另有责任书和安全考试的业务准入。

### Q4：为什么积分用流水账？

直接在 User 上修改余额无法解释余额来源，也不利于撤销和审计。流水账记录方向、数量、原因和 `balanceAfter`，支持漏洞奖励、商城扣减、取消返还和管理员调整。

### Q5：如何保证库存与积分一致？

在同一个 Prisma 事务中读取并校验商品、余额和库存，然后更新库存、写积分流水、创建兑换及事件。任何一步失败都回滚。高并发下还应进一步使用条件更新或数据库锁避免读后写竞争。

### Q6：AI 为什么不直接查询数据库？

模型不应持有数据库凭据，也不应自由决定查询范围。后端将允许的只读能力注册为工具，校验参数、角色和返回条数，再把脱敏结果交给模型。这样权限、审计和数据最小化都在可信代码中。

### Q7：如何防止 AI 幻觉影响业务？

- 实时业务查询优先由后端确定性返回。
- 模型输出经过 JSON 归一化和结构校验。
- 模型返回的业务 ID 必须命中后端白名单。
- 写操作只生成 Proposal，必须确认后由后端重新校验。
- 复测结论必须由执行证据约束。
- Agent 失败时走降级响应。

### Q8：为什么 AI 复测需要两个通道？

模板化 HTTP 检查可以在无凭据、无通用 Shell、固定预算的 Runner 中安全执行；复杂浏览器操作和多步推理需要 Agent，但风险更高，所以放到独立 Hermes Direct，增加目标范围、出网控制、凭据保险箱和人工审批。

### Q9：任务 Worker 如何避免重复执行？

当前使用 PostgreSQL 租约：

- `lockedAt`、`lockedBy` 标识持有者。
- 超过 TTL 的锁可恢复。
- `statusVersion` 做乐观并发。
- 状态迁移前校验合法边。
- 幂等键用于外部 Hermes run 创建。

当前限制是 Worker 与 API 同进程，下一步应迁移独立队列 Worker。

### Q10：凭据如何保护？

使用 AES-256-GCM 加密；密钥支持 key ID 和轮换；AAD 绑定 job、凭据类型和目标范围，防止密文被复制到其他任务使用；凭据有到期和销毁流程；日志和 artifact 只保留脱敏信息。

### Q11：附件为什么只允许 PDF？

缩小攻击面和解析范围。后端同时检查扩展名、MIME、magic bytes 和大小，而不是只信任浏览器 Content-Type；对象存储私有化，下载/预览经过权限校验和审计。

### Q12：知识为什么不能直接变成 Skill？

普通知识是具体问答，变化快且可能来自用户；Skill 会影响 Agent 的长期行为，风险更高。二者必须分层。用户会话只能在脱敏和审核后进入 KB，Skill 只能由管理员基于稳定的平台规则或方法论显式创建并二次审批。

### Q13：项目有哪些设计不足？

不要回答“没有”。建议回答：

1. Refresh Token 只完成了签发和存储，刷新/撤销接口未闭环。
2. Worker 目前是进程内轮询，不是真正 BullMQ。
3. 快速迭代造成 Hermes 拓扑文档不一致。
4. 前端没有正式路由，部分页面文件过大且有静态展示数据。
5. MinIO 使用手写 SigV4，生产维护应换成熟 SDK。

随后说明改进优先级。

### Q14：如果流量增长十倍怎么扩展？

1. API 无状态化并水平扩容。
2. Worker 从 API 进程拆出，使用 BullMQ/Redis。
3. AI 调用和复测任务做独立并发限制、配额与熔断。
4. MinIO/PostgreSQL 做生产级高可用、备份和连接池。
5. 热点查询缓存，但权限和实时状态避免长缓存。
6. 大表按时间和领域做索引、归档，审计与 artifact 设置保留策略。

### Q15：数据库最重要的索引是什么？

回答思路：

- 用户唯一标识：unifiedCode、email、studentNo。
- 漏洞列表：status、submitterId、updatedAt。
- 审计查询：actorId、targetType/targetId、createdAt。
- Worker：status、lockedAt、createdAt。
- AI Knowledge：status、canonicalKey、maintenanceStatus、updatedAt。
- 外键和唯一约束：一漏洞一个 assignment、一个 certificate、一个 retest plan/report 等。

具体以 Prisma Schema 和迁移为准。

### Q16：如何做监控？

当前已有 health 和数据库审计，但生产化还应补：

- API 延迟、错误率、数据库连接池。
- AI 调用成功率、耗时、token、降级率。
- Worker 队列深度、锁超时、重试和终态比例。
- Hermes SSE 断流和动作审批等待时长。
- MinIO 上传/下载失败。
- 业务指标：提交、审核 SLA、复测通过率、知识命中与负反馈。

## 6. 行为类问题

### 你遇到的最大困难是什么？

不要只说“代码多”。可讲 AI 复测：

> 最大困难是既要让 Agent 真正执行，又不能把安全边界交给模型。我把问题拆成计划、策略、审批、执行和证据五层，并用双通道把低风险模板和高风险 Agent 分开。实现过程中还处理了 SSE 断流、任务恢复、幂等和凭据生命周期。

### 你做过什么技术取舍？

> 当前使用模块化单体而不是微服务，优先保证漏洞、积分和审计事务一致性；Worker 先用 PostgreSQL 租约快速落地，但明确把独立队列作为下一阶段；MinIO Client 先手写最小 SigV4 减少依赖，但生产化应换 SDK。

### 如果重做一次会怎么改？

1. 先定义领域状态机和 API 契约。
2. 从第一天建立单一事实文档和 ADR。
3. Refresh Token、全局校验、异常格式和安全 Header 先做平台底座。
4. Worker 一开始就与 API 进程分离。
5. 前端从一开始使用路由和服务端状态管理。
6. 控制 Service/Page 文件大小，围绕领域能力拆分。

## 7. 面试禁区

- 不要声称 Redis/BullMQ 已经用于任务队列。
- 不要声称所有页面都已完全接入真实数据。
- 不要声称 Refresh Token 自动续期已完成。
- 不要把 AI 输出说成最终安全结论。
- 不要把 Hermes 和底层具体模型混为一谈。
- 不要回避文档漂移；把它转化为对工程事实源和治理的理解。
- 不要逐页介绍 UI，应围绕业务闭环、架构边界和技术难点讲。
