2	项目需求分析
2.1软件需求概述
本漏洞提交系统旨在为企业、安全团队及漏洞响应平台提供一套规范化、流程化的漏洞收集与管理解决方案。当前安全研究人员发现的漏洞数量持续增长，但传统提交通常依赖邮件或零散表格，存在信息格式不统一、处理进度不透明、追踪溯源困难、激励措施缺失等问题，导致漏洞信息流失或处理滞后。
系统面向以下典型应用场景：安全研究人员发现漏洞后通过统一入口提交信息并上传证明材料，实时跟踪处理状态；企业安全团队集中审核确认漏洞，分派给技术负责人修复，并将结果同步反馈给提交者；平台运营方通过积分、商城、电子证书等方式激励高质量提交，形成“提交-审核-修复-激励”的良性闭环。
从业务需求层面，系统需达成以下核心目标：实现漏洞信息标准化采集，确保关键要素完整可追溯；构建全流程透明化管理，增强用户信任感；建立科学的审核定级机制，保证评估客观性；设计可持续激励体系，激发用户参与热情；提供精细化权限管理与日志审计，保障安全合规。通过本系统建设，实现漏洞从发现到修复的全生命周期管理，有效提升整体安全防护水平。

2	用户管理	　用户可自行修改个人信息、查看个人资料；管理员可管理所有人的信息

5	漏洞处理	　技术负责人接收已确认漏洞，制定修复方案并实施修复，系统自动通知提交用户处理结果，用户可查看修复详情。

9	权限管理	　系统基于RBAC模型进行权限控制，定义超级管理员、审核管理员、技术负责人、普通用户等角色。
10	日志记录	　系统自动记录关键操作日志，包括用户登录登出、漏洞提交、审核操作、积分变动、权限变更等。

2.4项目用例分析
 
图2.1 提交者用例图
提交者是整个平台的核心贡献者，主要负责安全漏洞的发现与上报。提交者通过注册页面填写真实姓名、统一认证码、邮箱及密码等信息，申请加入白帽子计划，审核通过后即可登录平台。登录后，提交者可进入漏洞提交页面，填写漏洞标题、受影响地址、漏洞类型、自评等级及详细的漏洞描述与复现步骤，并上传证明附件，完成漏洞报告的上报。此外，提交者还可在积分商城中使用已获得的积分兑换各类实物或虚拟商品，并查看个人积分明细与兑换记录，全程体验激励体系带来的荣誉感与回报。
 
图2.2 审核员用例图
审核员是平台漏洞质量把控的关键角色，负责对已提交的漏洞进行技术验证与等级评定。审核员通过账号登录平台后，进入漏洞审核工作台，查看待审核漏洞列表，逐条查看漏洞详情与附件，并在测试环境中复现漏洞。根据复现结果，审核员依据CVSS标准或平台规则评定漏洞等级（高危/中危/低危），填写技术点评与审核批注，最终确认通过、驳回或打回补充。同时，审核员可参与证书管理，查看已颁发证书列表并下载PDF证书，部分权限下可对无效证书进行撤销操作，确保证书的权威性与准确性。
 
图2.3 管理员用例图
管理员是平台运营与维护的核心管理者，拥有系统最高权限。管理员登录后，可全面参与漏洞审核流程，具备与审核员相同的审核权限。同时，管理员通过漏洞管理模块查看全量漏洞列表，支持多维筛选、搜索、导出及漏洞状态编辑，实现漏洞全生命周期跟踪。在证书管理方面，管理员可手动颁发新证书、撤销无效证书并查看所有证书记录。此外，管理员负责公告管理，可发布、编辑、删除及置顶系统公告，控制生效时间与展示优先级；通过商城管理模块上架或下架积分商品，设置商品价格与库存；管理平台用户账号（禁用/启用、重置密码、角色分配）；并查看系统日志，审计关键操作记录，确保平台安全合规运行。
 

3	项目总体设计
本漏洞响应平台采用基于B/S架构的前后端分离设计，整体由运行环境、系统部署与软件架构三部分组成。前端沿用现有 React + TypeScript + Vite 工程，后端重构为基于 Go 语言的 Gin 服务，数据访问层采用 GORM 连接 MySQL 8.0，Redis 用于验证码、会话黑名单、热点数据缓存与限流计数。系统面向计划上线的校级真实环境设计，需兼顾论文展示价值、实际可运维性与后续横向扩展能力。网络拓扑上，用户通过浏览器经 HTTPS 访问 Nginx 反向代理层，Nginx 负责 TLS 终止、静态资源分发、跨域控制与请求转发；Go API 服务监听内部业务端口，处理认证、漏洞生命周期、积分商城、公告与证书等核心业务；MySQL 负责业务数据持久化，Redis 负责缓存与短期状态管理，数据库与缓存仅开放内网访问。软件架构方面，后端采用 Handler、Service、Repository 分层模式，配合中间件、配置中心、审计日志和 Swagger 文档生成，形成适合生产环境的高内聚、低耦合架构。

3.2系统部署设计/系统网络拓扑设计
本系统采用基于云服务器的分层部署架构，整体网络拓扑由用户访问层、接入层、应用层和数据层组成。用户通过浏览器访问前端站点，所有外部请求统一经过 HTTPS 接入 Nginx；Nginx 提供 TLS 证书管理、静态资源分发、反向代理和基础安全头控制，并将 API 请求转发至 Gin 应用服务。应用层采用 Docker 容器运行 Go 后端服务，可通过环境变量切换开发、测试与生产配置；后端服务通过 GORM 访问 MySQL，通过 go-redis 访问 Redis，并通过 Swagger 自动生成在线 API 文档。数据层中，MySQL 负责用户、漏洞、审核日志、积分、证书与公告等结构化数据持久化，Redis 负责邮箱验证码、登录限流计数、热点榜单缓存和短期令牌状态。数据库和缓存仅允许应用服务器所在内网访问，并通过独立账号、最小权限和定期备份保证数据安全。该部署方案具备前后端分离、容器化交付、便于扩容和安全隔离的特点，适合作为校级真实项目的上线基础方案。

3.3软件系统架构设计
本漏洞响应平台后端采用面向 Go 工程实践的分层架构设计，可划分为接口层、应用服务层、数据访问层和基础设施层。接口层由 Gin 路由、Handler 和认证中间件组成，负责请求接收、参数校验、统一响应和权限拦截；应用服务层负责封装漏洞审核、积分发放、证书签发、商城兑换等核心业务流程，并通过事务控制保证一致性；数据访问层基于 GORM 实现 Repository 模式，统一处理 MySQL 持久化和 Redis 缓存访问；基础设施层提供配置管理、结构化日志、邮件发送、文件存储、限流与 Swagger 文档等通用能力。该架构既保留了边界、控制、实体职责分离的思想，又更贴近 Go 语言在生产项目中的实现方式，能够支撑后续单元测试、容器化部署与模块扩展。

4	功能需求业务流程设计说明
本系统面向学生、审核员和管理员三类用户，提供漏洞全生命周期管理及配套功能。
学生端功能：学生可注册登录系统，管理个人信息。核心功能为提交漏洞，填写标题、类型、影响地址、详情并上传附件。提交后可查看“我的提交”，跟踪审核状态。学生还可浏览积分商城，使用获得的积分兑换物品，查看兑换记录。系统提供公告查看、消息通知接收以及证书查看下载功能。
审核员端功能：审核员负责漏洞审核工作，查看待审核漏洞列表及详细报告，判断漏洞有效性。可执行通过审核（并定级）、拒绝（填写理由）、标记重复或要求补充信息等操作。审核后可查看已处理漏洞，并浏览漏洞统计信息辅助决策。
管理员端功能：管理员进行全面系统管理，包括用户管理（增删改查、角色分配）、漏洞数据查看与统计、积分商城物品管理（上架、编辑、下架）、公告发布与维护、证书颁发与撤销，以及系统日志查看和基础参数设置。
4.1登录设计实现
 
图4.1 登录时序图
本系统登录模块采用基于角色的身份认证机制，支持学生、审核员、管理员三类用户使用学号/工号加密码进行登录。
认证流程：用户输入账号密码后，前端进行格式校验（账号为8-12位数字，密码长度6-20位），通过后加密传输至后端。后端接收请求，查询用户表验证账号是否存在及密码是否正确（密码采用bcrypt加密存储）。验证通过后，系统生成JWT令牌返回前端，令牌包含用户ID、姓名、角色等基本信息，有效期为8小时。
安全机制：登录页面集成图形验证码，防止暴力破解和自动化攻击。连续5次登录失败将临时锁定账号15分钟。所有登录操作均记录日志，包含IP地址、登录时间及结果，便于安全审计。支持“记住我”功能，可延长登录状态保持时间。
多端适配：登录界面采用响应式设计，在PC端和移动端均可正常显示和操作。退出登录时，前端清除本地令牌并跳转至登录页。

数据校验：后端接收请求后，首先校验验证码有效性，然后检查学号是否已存在（保证唯一性），并对手机号、邮箱格式进行二次验证。密码经bcrypt加密后存储，确保安全性。校验通过后，系统创建新用户账号，默认角色为“学生”，初始积分余额为0，账号状态为“正常”。

4.3漏洞提交设计实现
 
图4.3 漏洞提交时序图
本模块为学生提供标准化的漏洞报告提交通道，采用分步骤表单设计，确保信息完整性和提交效率。
表单设计：提报页面包含五个核心字段：漏洞标题（文本输入，限制5-50字符）、漏洞类型（下拉选择，预置XSS、SQL注入等常见类型）、影响地址（URL输入框，格式校验）、漏洞详情（富文本编辑器，支持图文混排）及附件上传区域。附件支持jpg/png/gif/mp4/pdf/zip格式，单个文件不超过20MB，前端实时显示上传进度。
交互流程：学生进入页面后，系统自动加载已有草稿（如有）。填写过程中，必填项以星号标注，失焦时进行实时校验并提示错误。点击“提交”按钮后，前端执行完整校验：必填项非空、附件格式大小合规、URL格式正确。校验通过后，数据封装为JSON格式与附件文件通过multipart/form-data方式异步提交至后端。
后端处理：接收请求后，系统进行二次校验和清洗，防止XSS攻击。生成唯一漏洞ID，记录提交者ID、提交时间等元数据，初始状态为“待审核”。使用数据库事务将漏洞主表信息与附件记录表同时写入，确保数据一致性。提交成功后，系统向学生发送站内信通知，并在“我的提交”列表展示新记录。同时触发相似度检查服务，为审核员提供去重参考。
4.4漏洞审核定级设计实现
 
图4.4 漏洞审核与定级时序图
本模块为审核员提供高效的漏洞审核与定级工具，支持对提报的漏洞进行真实性判断和危害等级评定。审核流程：审核员进入待审核列表，点击漏洞标题查看完整详情页。页面包含提交者信息、漏洞描述、附件预览及历史审核记录。审核员根据信息真实性，在页面底部操作区选择审核结果：通过审核：弹出定级面板，选择漏洞等级（高危/中危/低危），填写定级说明（可选）拒绝：弹出拒绝理由输入框（必填，限制500字符）标记重复：输入或选择原漏洞ID要求补充：填写需补充内容说明
定级逻辑：选择高危/中危/低危后，系统根据预设的积分规则自动计算奖励积分（如高危50分、中危20分、低危5分）。确认提交后，系统更新漏洞状态为“已定级”，同时触发积分奖励事务：扣除积分池、增加用户积分、记录积分变动日志，并生成站内信通知提交者。

兑换流程：用户在详情页点击“立即兑换”，系统弹出确认弹窗，显示物品名称、所需积分及当前积分余额。点击“确认兑换”后，前端发送兑换请求至后端。后端接收请求后执行严格校验：用户积分是否足够、物品库存是否充足、物品是否处于上架状态。校验通过后，开启数据库事务，依次执行扣减用户积分、减少物品库存、生成兑换记录三项操作，确保数据一致性。
并发控制：针对高并发场景下的超卖问题，采用数据库行级锁或乐观锁机制控制库存扣减。扣减库存时使用原子操作UPDATE goods SET stock = stock - 1 WHERE id = ? AND stock > 0，并在事务提交前校验受影响行数，防止库存扣为负数。
兑换记录：兑换成功后，系统生成兑换记录，包含兑换时间、物品名称、消耗积分、状态（实物为“待领取”，虚拟物品为“已完成”）。虚拟物品可自动显示兑换码或使用说明；实物物品显示领取地点和时间。用户可在“我的兑换”列表查看所有记录，并跟踪领取状态。系统同时记录积分变动日志，便于用户查询积分流水。

4	user_id	int	11		加索引，关联用户ID（获证人）

6	软件界面设计
本平台界面采用B/S架构下的响应式设计，遵循简洁直观、权限驱动、反馈及时的原则。通过分角色视图动态展示功能入口，关键操作配备二次确认与实时校验，确保用户体验流畅友好。数据统计区域优先采用可视化图表展示，帮助管理者快速掌握安全态势。
6.1登录页面设计
 
图6.1 登录界面
登录页面采用居中布局，上方展示平台LOGO及标题，下方为登录表单区，包含“统一认证码”和“密码”输入框、“安全登录”按钮及“没有账号？申请注册”链接。页面底部提供测试账号提示，便于评审与测试人员快速体验，符合易用性需求中的降低学习成本要求。输入框支持密码可见性切换，登录失败时弹窗提示具体错误原因。

图6.2 注册页面
