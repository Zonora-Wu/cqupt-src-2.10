本文档用于让新的 agent 或开发者快速理解当前数据库建模需求。早期讨论中的 L1-L6/X 授权层级已经不再作为正式落地模型；当前正式模型采用 `BASIC / TRUSTED / STAFF` 三层授权等级，并用授权来源表适配不同学校、不同交付模式。

## 1. 用户与注册登录

1. 当前只允许校内用户注册。
2. 访客不入库，只允许使用未登录首页的公开证书查询功能。
3. 用户登录方式包括统一认证码 + 密码、邮箱验证码。
4. 用户字段需要包含：姓名、统一认证码、邮箱、学院、年级、学号、身份说明、授权等级、授权来源。
5. 不需要专业字段，学院即可满足当前建模。
6. 一个用户只能拥有一个角色。
7. 用户角色只包含：学生、审核员、管理员。
8. 不需要超级管理员。

## 2. 授权模型

正式授权模型拆成三部分：

```text
角色 Role：决定用户能使用哪些功能。
授权等级 AuthorizationLevel：决定用户默认可测试的资产范围。
授权来源 AuthorizationSource：说明用户为什么获得该授权。
```

授权等级：

| 等级 | 含义 | 默认适用对象 |
|---|---|---|
| BASIC | 基础授权 | 普通校内学生、完成准入条件的用户 |
| TRUSTED | 可信授权 | 安全团队、实验室、社团、课程班、专项培养对象 |
| STAFF | 教职工/管理授权 | 信息化办老师、安全老师、平台运营老师 |

资产范围：

| 范围 | 含义 |
|---|---|
| PUBLIC | 公开授权测试资产 |
| INTERNAL | 内部授权资产 |
| SPECIAL | 专项任务资产 |

默认授权策略：

| 授权等级 | PUBLIC | INTERNAL | SPECIAL |
|---|---|---|---|
| BASIC | 允许 | 不允许 | 不允许 |
| TRUSTED | 允许 | 允许 | 不允许 |
| STAFF | 允许 | 允许 | 允许 |

授权来源不写死为枚举，使用 `authorization_sources` 表配置。CQUPT 可配置蓝山安全组、红岩网校安全组、信息安全协会、安法学院学生、研究生导师备案、线上安全考试、信息化办教职工专项、管理员手动授权等来源；其他学校可以替换为自己的组织、课程、实验室或白名单来源。

## 3. 准入与责任书

1. 用户必须绑定邮箱并签署责任书后才可以提交漏洞。
2. 后续可增加答题分数合格要求。
3. 答题只需要记录通过 / 未通过，可选记录分数和时间，不需要保存详细题目。
4. 责任书需要保存版本、签署时间、IP、设备信息等关键审计字段。

## 4. 漏洞报告

漏洞报告字段至少包含：

- 标题
- 资产
- URL
- 漏洞类型
- 自评等级
- 复现步骤
- 影响评估
- 修复建议
- 附件信息

漏洞等级：

```text
严重 / 高危 / 中危 / 低危 / 信息
```

业务规则：

1. 漏洞允许保存草稿。
2. 漏洞已提交后不能撤回。
3. 漏洞只分配一个审核员。
4. 审核员可以审核、管理漏洞、复测。
5. 每次状态变更需要记录操作人、时间、IP、设备信息。

## 5. 附件

1. 上传类型只允许 PDF。
2. 单个文件不超过 10MB。
3. 需要保存文件大小、哈希、MIME、上传人、上传时间。
4. 附件只有提交本人、审核员、管理员可以查看。
5. 查看敏感附件必须写入审计日志。
6. 复测可以上传 PDF 文件，但不是必须。

## 6. 证书

1. 审核员和管理员都可以签发证书。
2. 审核员签发证书的权限需要管理员开启。
3. 证书当前只有一种类型。
4. 一个漏洞最多一张证书。
5. 证书为线上电子证书，需要支持真实 PDF 文件。
6. 访客可以通过证书编号公开查询，但返回信息必须脱敏，不能给出漏洞敏感详情。
7. 证书撤销需要保留记录，不能物理删除。

## 7. 积分与商城

1. 积分由审核员或管理员根据漏洞最终等级手动确定。
2. 积分必须有完整流水。
3. 积分可以手动调整，但必须记录原因与操作人。
4. 商品兑换采用校园线下领取，不需要邮寄地址。
5. 兑换状态包含：待领取、已领取、已取消。

## 8. 学习中心

1. 学习中心合并工具资源与靶场资源。
2. 前期靶场只引入外部链接。
3. 后续可能开发本地靶场实例，因此数据库需要保留扩展字段。
4. 资源可以统计下载次数或访问次数，其余统计暂不需要。

## 9. 公告

1. 审核员和管理员都可以管理公告。
2. 发布范围包括：全体用户、学生、审核员、管理员。
3. 公告需要支持草稿、发布、下架、置顶。
4. 不需要记录公告阅读状态。

## 10. AI

1. 学生、审核员、管理员各自使用隔离的 AI 空间，不能互通。
2. 同一角色内可以复用被蒸馏后的 skill 和常见问题答案。
3. 登录退出后不长期保存原始对话记录。
4. 只保存脱敏后的输入摘要、输出摘要、AI 调用审计。
5. 对话中有价值的部分可以蒸馏为 skill 保存。
6. 常被问的问题可以保存为 FAQ，供同角色用户复用。
7. AI 对系统的任何操作都必须生成人工确认项，不能自动执行敏感操作。
8. Hermes Agent 初期部署在同一服务器，但必须通过后端 AI Gateway 调用，前端不能直连 AI 服务。

## 11. 审计日志

必须审计：

- 登录
- 退出
- 提交漏洞
- 查看敏感附件
- 审核操作
- 漏洞状态变更
- 证书签发 / 撤销
- 公告发布
- 用户权限变更
- 系统设置变更
- AI 调用

审计日志建议默认保留 3 年，后续按学校要求调整为 5 年或长期保留。

## 12. 部署与交付

1. 当前不做多租户，每个学校独立部署。
2. 需要支持本地开发、Docker 部署、Ubuntu 云服务器部署。
3. 需要保留学校配置表，用于不同学校替换 Logo、主题色、邮箱域名、规则文本、证书模板等。
4. 系统配置应支持实时生效，关键参数修改需要弹框确认并写入审计日志。
